# ShareIt

Сервис для шеринга вещей: пользователи публикуют вещи, которыми готовы поделиться,
и берут в аренду вещи других пользователей. Бронирование (`Booking`) закрывает вещь от
других пользователей на время аренды. После завершения аренды арендатор может оставить
отзыв на вещь. Если нужной вещи нет в сервисе, пользователь может оставить запрос
(`ItemRequest`) с описанием, а другие пользователи — ответить на него, добавив
подходящую вещь.

Приложение разбито на два независимых Java-приложения, живущих в одном Maven-реакторе
и общающихся по REST:

- **`server`** (порт `9090`) — вся бизнес-логика и работа с БД (PostgreSQL через
  Spring Data JPA / Hibernate). Валидацию формата входных данных не делает — считает,
  что запрос уже проверен на gateway.
- **`gateway`** (порт `8080`) — тонкий слой, с которым работают клиенты. Проверяет
  формат входных данных (Bean Validation) и всё, что не требует обращения к БД, и
  прозрачно проксирует запрос на `server`, возвращая клиенту тот же статус и тело
  ответа. Если `server` недоступен или не отвечает — возвращает `503` вместо обрыва.

## Стек

- Java 21, Spring Boot 3.3.2 (Spring MVC, Spring Data JPA)
- Многомодульный Maven-проект (`server` + `gateway`, общий родительский `pom.xml`)
- PostgreSQL (прод), H2 (тесты) — только в `server`
- `RestTemplate` + Apache HttpClient5 — в `gateway`, для обращения к `server`
- Bean Validation (`spring-boot-starter-validation`) — только в `gateway`
- Lombok
- Checkstyle + SpotBugs (профиль `check`), JaCoCo (профиль `coverage`, пороги: 90% строк, 60% ветвей)

## Запуск

> На хосте с несколькими установленными JDK убедитесь, что сборка идёт под
> **JDK 21** (`java.version` в корневом `pom.xml`). Maven может по умолчанию
> подхватить более новую JDK (например, 23 или 26) — с некоторыми их сборками
> Lombok в этой связке не генерирует геттеры/сеттеры. Это ограничение самого
> Lombok, не связанное с кодом проекта; фиксируется через `JAVA_HOME`:
> ```bash
> export JAVA_HOME=$(/usr/libexec/java_home -v 21)
> ```

Собрать оба модуля одной командой из корня репозитория:

```bash
mvn clean install
```

### Вариант 1 — всё через Docker Compose

Поднимает `gateway`, `server` и `postgres` одной командой:

```bash
docker compose up -d --build
```

`gateway` слушает `localhost:8080`, `server` — `localhost:9090`, Postgres внутри
контейнеров — `postgres:shareit@db:5432/shareit` (наружу проброшен на `6541`).
Таблицы создаются автоматически при старте `server` из `server/src/main/resources/schema.sql`
(`CREATE TABLE IF NOT EXISTS` — безопасно перезапускать сколько угодно раз).

```bash
docker compose down       # остановить, данные останутся в volume
docker compose down -v    # остановить и стереть данные
```

### Вариант 2 — локально (например, из IDE)

`server` ожидает PostgreSQL на `localhost:5432`, база `shareit`, пользователь/пароль
`test`/`test` (см. `server/src/main/resources/application.properties`) — поднимите
свой локальный Postgres с этими параметрами. Затем запустите оба приложения как
отдельные Spring Boot джары (порядок важен — `gateway` должен достучаться до `server`):

```bash
mvn -pl server spring-boot:run
mvn -pl gateway spring-boot:run
```

## Тесты

```bash
mvn clean install                 # все тесты обоих модулей
mvn -Pcheck clean verify          # + Checkstyle и SpotBugs
mvn -Pcoverage -pl server -am clean verify   # + JaCoCo для server
mvn -Pcoverage -pl gateway -am clean verify  # + JaCoCo для gateway
```

Тесты `server` используют H2 в режиме совместимости с PostgreSQL
(`application-test.properties`), отдельная база Postgres для них не нужна.
Покрытие: интеграционные тесты на реальной БД (по одному на каждый крупный метод
сервиса), MockMVC-тесты всех REST-эндпоинтов обоих модулей с замоканным
сервисным/клиентским слоем, `@JsonTest` для DTO с датами.

## API

Все запросы проходят через `gateway` (`localhost:8080`) — именно этот адрес нужен
клиентам, включая Postman-коллекцию.

### Users

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/users` | Создать пользователя |
| `GET` | `/users` | Список всех пользователей |
| `GET` | `/users/{userId}` | Получить пользователя по id |
| `PATCH` | `/users/{userId}` | Частично обновить пользователя (имя и/или email) |
| `DELETE` | `/users/{userId}` | Удалить пользователя |

### Items

Во всех запросах, кроме поиска и просмотра конкретной вещи, требуется заголовок
`X-Sharer-User-Id` — id пользователя, от лица которого выполняется запрос.

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/items` | Добавить вещь. Пользователь из `X-Sharer-User-Id` становится владельцем. Можно указать `requestId`, если вещь добавляется в ответ на чей-то запрос — необязательно |
| `PATCH` | `/items/{itemId}` | Изменить название/описание/доступность. Только владелец |
| `GET` | `/items/{itemId}` | Просмотреть вещь по id (доступно любому пользователю), с отзывами |
| `GET` | `/items` | Список вещей владельца — с отзывами и датами последнего/ближайшего бронирования |
| `GET` | `/items/search?text={text}` | Поиск доступных для аренды вещей по названию/описанию |
| `POST` | `/items/{itemId}/comment` | Оставить отзыв на вещь. Только если аренда уже завершена |

### Bookings

Во всех запросах требуется заголовок `X-Sharer-User-Id`.

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/bookings` | Забронировать вещь (статус `WAITING`) |
| `PATCH` | `/bookings/{bookingId}?approved={true\|false}` | Подтвердить/отклонить бронирование. Только владелец вещи |
| `GET` | `/bookings/{bookingId}` | Получить бронирование. Только автор или владелец вещи |
| `GET` | `/bookings?state={state}` | Бронирования текущего пользователя как арендатора |
| `GET` | `/bookings/owner?state={state}` | Бронирования по всем вещам текущего пользователя-владельца |

`state` — один из `ALL` (по умолчанию), `CURRENT`, `PAST`, `FUTURE`, `WAITING`, `REJECTED`.
Результат отсортирован от новых бронирований к старым.

### Requests

Во всех запросах требуется заголовок `X-Sharer-User-Id`.

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/requests` | Создать запрос на вещь (описание того, что нужно) |
| `GET` | `/requests` | Собственные запросы с ответами на них (вещи, добавленные в ответ) |
| `GET` | `/requests/all` | Запросы других пользователей |
| `GET` | `/requests/{requestId}` | Один запрос с ответами на него. Доступно любому пользователю |

Запросы отсортированы от новых к старым; ответ на запрос — список вещей в формате
`id`, название, `id` владельца.

## Обработка ошибок

- `400 Bad Request` — не прошла валидация входных данных (на `gateway`) или бизнес-правило
  на `server` (например, вещь недоступна, отзыв без завершённой аренды, неизвестное
  значение `state`, дата окончания бронирования раньше даты начала)
- `403 Forbidden` — попытка редактировать вещь или подтвердить бронирование не её владельцем
- `404 Not Found` — пользователь, вещь, бронирование или запрос не найдены; либо владелец
  пытается забронировать собственную вещь; либо бронирование запрашивает посторонний
- `405 Method Not Allowed` — вызов эндпоинта неподдерживаемым HTTP-методом
- `409 Conflict` — email уже занят другим пользователем, либо у удаляемого пользователя
  остались вещи/бронирования/отзывы/запросы
- `503 Service Unavailable` — от `gateway`, если `server` недоступен или не отвечает

Ответ об ошибке: `{"error": "текст сообщения"}` — единый формат на обоих модулях.
